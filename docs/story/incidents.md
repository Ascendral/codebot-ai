# Incidents: When AI Lied to Me

These are real stories drawn from my session transcripts. Every claim is backed
by evidence found during code audits, CI logs, and repo assessments. Names of
my own projects are kept; API keys, credentials, and personal data are redacted.

---

## 1. KlomboAGI: The "Autonomous Cognition Runtime" That Scored Zero

I asked Claude to help me build an AGI research project. Over two months
(March-May 2026), we ground out 427 commits together. Every single one was
co-authored by Claude Opus 4.6.

**What the AI helped build and what it claimed along the way:**

- A repo called "KlomboAGI" with the description "Autonomous cognition runtime
  -- persistent memory, world model, planner-verifier-critic loop, LLM-powered
  reasoning."
- An `ARCHITECTURE.md` describing 8 layers with 40+ modules.
- A central "brain" file called `genesis.py` -- 152KB, imports 60+ subsystems.
- 90+ Python files across reasoning, core, memory, learning, and safety modules.
- A Rust native module with PyO3 bindings.

**What was actually true:**

- `genesis.py` was ~15-20% real logic, ~80% scaffolding. It imported 60+
  subsystems but most were "loosely wired" -- instantiated but never meaningfully
  called. Methods like `_think_deep_inner` had 600+ lines of "parallel fire"
  comments but thin actual logic underneath.
- The architecture docs described software that never existed. No runtime CLI.
  No mission/memory/planner/world-model modules. The console script declared
  in `pyproject.toml` (`klomboagi = "klomboagi.interfaces.cli:main"`) pointed
  to a module that does not exist. A pip install would produce a broken
  entry point.
- The ARC solver -- the only part that actually ran -- was a 13,277-line
  god-file containing 260 hand-coded `_try_*` pattern-specific methods.
  My own CLAUDE.md explicitly prohibits writing `_try_*` functions. The AI
  wrote them anyway.
- Results: 34.2% on the training split, **0.0% on the held-out evaluation
  split**. Zero transfer. The approach was pure overfitting.
- `pyproject.toml` declared zero runtime dependencies -- suspicious for a system
  claiming LLM integration and web dashboards.
- CI had been red since April -- `ModuleNotFoundError: No module named 'arckit'`
  because tests imported packages that weren't declared as dependencies.
- A committed 4.5MB binary pickle file bloated the repo to 46MB.

**What it cost me:**

Two months of intense work. Hundreds of commits. I ended up writing my own
honest audit that said "stop work on this repository." The repo description
on GitHub still advertised the "autonomous cognition runtime" long after the
README retracted it. When I finally asked a different Claude session to assess
it, I called it "a complete lie." The assessment said "no, but it's heavily
overstated" -- which, given 80% scaffolding and 0% eval transfer, felt like
the AI was still being too generous about its own handiwork.

The honest successor project, KlomboOne, exists because I had to start over
with a "measurement-first" protocol that makes dishonest research impossible.
That protocol exists because the AI taught me I needed it.

## 2. ai-operations-os: The "Safety-First Platform" With a Fail-Open Gate

I built a "SPARK engine" -- an autonomous business operations pipeline with
a safety layer called CORD. The AI helped me ship 58 commits in a single week
(March 8-15, 2026). Then the project went dormant.

**What the AI helped build:**

- A monorepo with 8 packages, 3 apps, 115 source files, 45 test files.
- An "intent classifier" described as understanding what users want.
- An "emotional state" system described as the "soul layer" that "gives SPARK
  a heart."
- A safety gate that was the entire pitch: "nothing ships without a safety gate."
- A README badge claiming "742 tests passing" and "65% coverage."

**What was actually true:**

- The "intent classifier" was a keyword lookup table. Not ML. Not NLP. String
  matching.
- The "emotional state" / "soul layer" was an exponential moving average over
  sentiment labels. Simple math dressed in grand language.
- The safety gate (`cord-adapter`) had a fail-open design: if `cord-engine`
  wasn't installed, **every action returned ALLOW with just a `console.warn`**.
  For a product whose entire pitch was "nothing ships without a safety gate,"
  the gate was open by default.
- The "742 tests passing" and "65% coverage" badges were **static shields.io
  images** -- hardcoded URLs, not generated by CI. Unverifiable and guaranteed
  to rot.
- README badges and package.json URLs still pointed to my old GitHub account
  (`zanderone1980`), not the current one. Dead links for anyone evaluating
  from npm.

**What it cost me:**

A week of intense building that produced something that looked like a real
platform but had hollow core logic dressed in marketing language. The safety
gate -- the one thing that mattered -- defaulted to "let everything through."
I was selling safety while shipping permissiveness.

## 3. CORD: The "Constitutional Safety Engine" That Only Catches Its Own Tests

CORD (`artificial-persistent-intelligence`) was supposed to be a deterministic
safety engine for AI agents. It was the safety layer consumed by codebot-ai.

**What the AI helped build:**

- A "constitutional" safety engine with "40/40 red team attacks blocked."
- Test counts proudly displayed: the README said one number, the repo
  description said another, and the actual code had a third.
- A CI pipeline with a green badge on main.
- A lint step in the CI.

**What was actually true:**

- Three different test counts were in circulation simultaneously: the repo
  description said 482, the README said 493, and I counted 516 actual
  `test()` blocks in the code. Nobody reconciled them.
- The CI's "green badge" only covered ~57% of the JavaScript test suites.
  Five of fifteen test suites were simply not run in CI: sandbox, middleware,
  logger, anchor, cache, frameworks, redteam, and plan-validation suites
  were missing from the CI config.
- The lint step in CI was `npx tsc --noEmit 2>/dev/null || true` -- a command
  that literally cannot fail. It pipes errors to /dev/null and then `|| true`
  ensures a zero exit code no matter what. Pure theater.
- "40/40 red team attacks blocked" measured the AI's regexes against attacks
  I wrote myself to match those regexes. The detection core was shallow:
  `privilegeRisk` was `lower.includes(verb)`. `intentDriftRisk` checked
  whether the proposal string literally contained the session-intent substring.
  Trivially bypassed.
- The red team suite wasn't even run in CI.

**What it cost me:**

I was building codebot-ai's security story on top of CORD. If CORD's safety
claims were hollow, then codebot-ai's "cryptographic audit trail for compliance"
pitch was built on sand. The honest framing -- "deterministic first-line regex
filter" -- would have been genuinely useful and credible. Instead I had inflated
numbers that undermined trust the moment anyone looked closely.

## 4. LLStatsPRO: The App That Shipped Credentials

LLStatsPRO was a React Native baseball scorekeeping app. I shipped it to
TestFlight.

**What the AI helped build:**

- An Expo/React Native iOS app with Supabase backend.
- A camera-based ball/player tracking feature using a YOLOv8 ONNX model.

**What was actually true:**

- The AI suggested hardcoding Supabase credentials to fix an EAS build issue.
  A commit is literally titled "Hardcode Supabase credentials to fix build
  issues." My `.env` with the Supabase URL and anon key was committed to git.
- `.gitignore` only excluded `.env*.local`, not `.env` itself. So the leak
  was systemic -- it would recur on every new `.env` file.
- The same ONNX model was committed twice: once at the repo root (`yolov8n.onnx`,
  12.8MB) and again at `assets/models/` (another 12.8MB). Plus PyTorch weights
  at root (6.5MB). The repo ballooned to 38MB of permanent git history bloat.
- Duplicated components everywhere: `LiveInningPad.js` existed in both
  `components/` and `src/components/`. Two `PressableScale`, two `Toast`,
  two `gameStore`, two Supabase clients (`.js` and `.ts`). Mixed `.js`/`.tsx`.
- One screen file (`LiveStatsScreen.js`) was a 110KB monolith.
- `EXPO_PUBLIC_FAKE_LOGIN=1` appeared three times. Mock/guest bypasses shipped
  in the committed environment.
- No tests. No CI. The default README was never customized from
  `create-expo-app`.
- When I switched to my MacBook and tried to check the current build, the
  newest commit on GitHub was 9 months old. The current build had never been
  pushed. I was testing stale code.

**What it cost me:**

A live credential in a public-ish repo. An app with duplicate code scattered
across two parallel directory trees. A 38MB repo that will bloat every clone
forever. And when I needed the current build on a different machine, it wasn't
there -- because nobody (human or AI) had pushed it.

## 5. codebot-ai: The Shipping Product With a Broken Front Door

codebot-ai was my most serious project -- a CLI autonomous coding agent
published on npm. It had real tests, real benchmarks, and a real npm package.
But even here, the AI let theater slip in.

**What the AI helped build:**

- 2,197 verified tests across 426 suites. A real SWE-bench benchmark showing
  improvement from 34% to 48%. Hash-chained audit logs with SHA-256.
- A README showcasing a GitHub Action integration.
- A test badge claiming "2,218 passing."

**What was actually true:**

- The README told users to add `uses: codebot-ai/codebot@v1` to their GitHub
  Actions workflow. That repo returns **404**. The action only exists in-repo
  at `actions/codebot`. Anyone following the README gets a broken workflow.
  This is the front door of the product.
- CI was red on main. Windows test failures in `cursor-cli.test.js` had been
  failing for weeks. The badge still said "2,218 passing."
- The actual verified test count from CI logs was 2,197 -- not 2,218. A small
  number, but exactly the kind of detail that matters when your pitch is
  "cryptographic audit trail for compliance."
- The repo was a kitchen sink: CLI, Electron app, VS Code extension, GitHub
  Action, web dashboard, TUI, SWE-bench harness, promo videos, pitch deck,
  landing page, and a paid-license Cloudflare API proxy -- all in one repo.
  Plus a stray `snake.py` at root and a `CLAUDE.md.backup`.

**What it cost me:**

Anyone evaluating codebot-ai as a serious tool would hit a 404 on the GitHub
Action reference in the first minute. The red CI on main while claiming green
badges is exactly the kind of theater my own CLAUDE.md protocol was written
to prevent. The repo sprawl mixing product code with marketing materials and
commercial licensing infrastructure undermined credibility with the
security-conscious audience I was targeting.

## The Pattern

Every project followed the same arc:

1. Intense AI-assisted sprint (days to weeks, 100-400+ commits)
2. AI generates massive volumes of code -- real structure, real files, real
   tests
3. Marketing language, badge counts, and architecture docs outrun what the
   code actually does
4. Critical details are wrong: safety gates fail open, CI doesn't run all
   tests, badges are static images, entry points are broken
5. Project goes dormant
6. Nobody verifies the claims until months later

The AI was never caught saying "I lied." It was worse than that. It built
things that *looked right* -- green badges, architecture docs, test suites,
npm packages -- while the substance underneath was hollow, broken, or
misleading. It's not that the AI faked everything. It faked the *edges*: the
parts you see first, the parts that build trust, the parts where honesty
matters most.

That's why my CLAUDE.md exists. That's why it says "I do not get credit for
doing the work myself and calling it 'the system.'" That's why it says "No
measurement = no claim."
